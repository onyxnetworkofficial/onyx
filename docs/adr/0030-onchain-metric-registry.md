# ADR-0030: On-chain metric registry, attested preflight and proof level

## Status
Accepted, 2026-10-11 (the loop decides, per the owner's instruction to keep the project moving).
Implemented in `contracts/src/OnyxRegistry.sol` (deploy: `contracts/script/DeployRegistry.s.sol`),
`crates/onyx-core/src/onchain.rs` and `onyx_coordinator::recompute::within_preflight_budget`;
vectors `fixtures/registry/vectors.json` (generated by
`adapters/source-fiscaldata/tests/registry_vectors.rs`, read by `contracts/test/OnyxRegistry.t.sol`).
Wired into `scripts/demo-local.sh` and `scripts/demo-testnet.sh`.

## Context
Four TODOs were left on chain by levels 1 and 2:
- L2SRC residual: level-2 feed templates live in one coordinator's store; a rogue coordinator
  registers its own template in its own store.
- L2R2-F2: the proof level is advisory at the API; nothing a consumer verifies on chain carries it.
- L2R3-F5 / L2R4-F2: one level-2 result per fact holds inside one store, not across coordinators.
- SER-R2-F1: the settlement's `openRound` trusts the coordinator to have run the preflight.

`OnyxSettlement` has about 1.4 KB of bytecode margin, so none of this can go into it.

## Decision
1. **A separate contract, `OnyxRegistry`,** reads the settlement (`coordinator`, `shardState`,
   `isFinal`, `verifyRow`) and never writes to it. The settlement and its vectors are unchanged.
   (Kinds: `Recipe` for level 1; `Feed` or `DatedFeed` for level 2.)
2. **One template per metric, append-only, set by the owner.** `metrics[keccak256(utf8(metric))]`
   holds `(kind, template)`: kind `Recipe` (level 1, the template is the recipe id), `Feed` (level
   2, a fixed subject: one fact per window end) or `DatedFeed` (level 2, a dated subject: one fact
   per date whatever the window); for level 2 the template is `onyx_core::FeedTemplate::id`. The
   chain cannot read a template, so the level-2 kind is derived from it by
   `onyx_core::onchain::MetricKind::of` on every registration path, and a consumer refuses a
   metric whose registered kind or template id differs from its own copy's (REG-R2-F2). A
   registered metric never changes. The owner is one key on testnet; a multisig or timelock owner
   is a TODO before any mainnet use.
3. **Preflight attestation before the open (amended, REG-R1-F1, REG-R2-F1).** `attestShard(round,
   preimage, runtime, metric, fuelUsed, level)`, only from the settlement's coordinator, where
   `runtime` is the Borsh `RuntimeProfile` the shard commits to (its keccak must be the preimage's
   runtime hash; the fuel limit is read out of it, never passed separately), and `preimage` is
   every field the shard id hashes (recipe id, runtime, label set, source, schema, rights, params
   hash, registry root). ENFORCED on chain: the shard id is recomputed from the preimage (so the
   recipe and label set checked are the ones the shard commits to); the preimage's recipe is the
   metric's registered recipe; a labelled shard's label set is registered by the owner
   (`registerLabelSet`) and the level is no better than the label set's level; 1 <= level <= 5
   (6, an unstaked claim, is never a shard's level); `fuelUsed * 1e6 <= fuelLimit * 500_000` with
   the committed limit; once per (round, shard); only while the shard is still `None`. ATTESTED
   (the coordinator's word, no on-chain rerun): the fuel used, and the level wherever it is above
   its floor. An unlabelled shard has no floor: labels moved into the params or the source are
   attested, not floored (REG-R2-F4). A rerun can check the fuel figure against the pinned recipe
   and inputs off chain; nothing on chain compares them.
4. **The level is bound into the consumer's verify path.** `verifyRowLeveled(...)` returns
   `(verifyRow(...), attested level, metric)`, and `(false, 0, 0)` for a shard that is not final or
   was never attested. `levelOf(round, shard)` likewise. Consumers that check rows through the
   registry therefore cannot accept a row from an unattested shard. The settlement's own `verifyRow`
   stays as it was (level-free) for existing callers.
5. **One level-2 result per fact (amended, REG-R1-F2).** `recordObservation(metric, subjectKey,
   windowEnd, spec, result)`, only from the coordinator, which records value outcomes only
   (attested; the contract sees no outcome; SEC-R1-F1, SEC-R2-F3). ENFORCED on chain: the fact key
   `keccak256("onyx-registry-fact-v1" ‖ metric ‖ registered template ‖ subjectKey ‖ windowEnd, 0
   for a `DatedFeed`)` is computed here from the metric's REGISTERED template (no template argument
   is taken, so a substituted template can never fill the fact), and each fact is set once. RECORDED,
   not derived: `spec` (the round's `ObservationSpec::id`) and `result`
   (`ObservationSettlement::result_hash`). The chain cannot instantiate a feed template (Borsh spec,
   business-day calendar), so a consumer instantiates the registered template for the subject and the
   recorded window itself and calls `observationLevel(metric, subjectKey, windowEnd, spec, result)`,
   which is 2 only when the recorded spec and result equal what it passes. The consumer builds BOTH
   itself with `onyx_coordinator::observe::onchain_observation_check`: it checks the registration
   against its template copy, instantiates the spec, recomputes the round id, checks every reveal
   against its commit and re-aggregates the result hash (REG-R2-F3). Passing back the spec and
   result read from `observationOf` (or from an API) compares a record with itself and proves
   nothing. A coordinator that records a wrong spec or result can block that fact (liveness) but
   cannot get such a consumer to accept it. Result hashes are not unique across facts (equal values
   on two dates both record, REG-R1-F5).
6. **The owner is never the coordinator's key (REG-R1-F3).** The constructor refuses
   `owner == ledger.coordinator()`, and `DeployRegistry` requires `ONYX_REGISTRY_OWNER` and refuses
   the deployer (who is the coordinator in `Deploy.s.sol`). The separation is between KEYS, not
   parties: an owner and a coordinator who collude can register any label-set level and attest any
   level at or above it. The demos hold both keys in one driver process and register the level the
   coordinator computed (REG-R2-F5); a deployment that relies on the separation needs the owner key
   held by someone else.

## Consequences
- A coordinator can no longer choose a metric's template or a label set's level: the registry owner
  (never the coordinator) does, once. What the chain enforces and what it only records as the
  coordinator's word is split per item above; the fuel used, the level above its floor (and the
  whole level of an unlabelled shard), and the level-2 spec id and result hash are attested, not
  proven. Owner and coordinator are separate keys, not necessarily separate parties (item 6).
- A consumer that verifies through the registry gets the level and fails closed on unattested
  shards. `onyx-api` still reports the level from its catalog (advisory); reading it from the
  registry is a TODO (`ChainRoots` would need the registry address and one more `eth_call`).
- `openRound` itself still does not require an attestation (the settlement is at its size limit);
  a shard opened without one is simply never verifiable through the registry.
- The owner key is a new trust root (testnet only); it can register but never change or delete.

## Amendment (REG-F, 2026-10-11): the level floor is keyed by recipe and applied on read

1. The floor is stored per RECIPE (`recipeMinLevel[recipeId]`), not per metric: a second metric
   registered with the same recipe inherits it and cannot register a weaker one (REG-F-F2).
   `metricMinLevel(metric)` is a view of its recipe's floor (0 for feed metrics).
2. `registerMetric(metric, kind, template, minLevel)` sets a recipe metric's floor in the same
   transaction, so no attestation can land between the two (REG-F-F1). `minLevel` must be 0 for
   a feed metric. `registerMetricMinLevel` remains for a recipe metric registered without one
   (append-only; refuses feed metrics).
3. `levelOf` (and so `verifyRowLeveled`) returns max(attested level, the recipe's current floor):
   a floor set after an attestation still applies (REG-F-F1).
4. `onyx-node` reads `attestationOf` too and treats a shard attested under a metric other than its
   catalog metric as unattested (weakest level) (REG-F-F2).
5. The demo drivers register every floored metric (`METRIC_MIN_LEVELS`) with its recipe and floor
   in one owner call and show the floor on chain with two dry-run attestations (below: refused,
   at the floor: passes) (REG-F-F3). `DeployRegistry` only deploys; registrations are the owner's
   driver step.


## Amendment (L2RND-R1, 2026-10-11): level-2 observer draws are announced on chain
1. **Why.** Review L2RND-R1 showed the level-2 draw was grindable: the beacon, the chain height
   at announcement, the attempt and the pool were the coordinator's word (THREATS L2-F2).
2. **Storage.** Per fact key: `drawCount` and, per attempt, `Draw { pool, beaconHeight,
   announcedAt, beacon }`.
3. **Calls.** `announceDraw(metric, subjectKey, windowEnd, attempt, pool, beaconHeight)`
   (coordinator only; the metric must be registered and the fact unrecorded; `attempt ==
   drawCount < MAX_DRAW_ATTEMPTS = 64`; `beaconHeight > block.number`). `fixBeacon(fact, attempt)`
   (anyone, once, after the beacon block and within 256 blocks: `blockhash`). `drawOf(fact,
   attempt)` and `drawMatches(...)` (views). `recordObservation` requires the fact's latest draw
   to have a fixed beacon (`NoDraw`). Events `DrawAnnounced`, `BeaconFixed`.
4. **Size.** `OnyxRegistry` runtime 8,228 bytes (limit 24,576).
5. **Residuals.** Sequencer bias of an L2 block hash (ADR-0022 item 5); the pool hash is
   attested; up to 64 public attempts per fact (ADR-0027 amendment 6, point 8), now bounded per
   subject (below).
6. **Subject bound (review L2RND-R2).** Storage `subjectStrikes` and `subjectReopens` per
   `subjectDrawKey(metric, subjectKey) = keccak256("onyx-registry-subject-draws-v1" ‖ metric ‖
   subjectKey)` (Rust `onchain::subject_draw_key`, vector `subjectDrawKeys`). `announceDraw`
   reverts `DrawsExhausted` once the subject holds `MAX_DRAWS * (1 + reopens)` draws without a
   recorded value (`MAX_DRAWS` = 3), then adds one; `recordObservation` takes one off.
   `reopenDraws(metric, subjectKey)` is owner only (the owner is never the coordinator) and emits
   `DrawsReopened`; `drawBudget(metric, subjectKey)` returns (strikes, allowance). No grid check
   on chain: the subject bound covers every window. Runtime 8,985 bytes (limit 24,576).
7. **Draw commitment (review L2RND-R3).** `Draw.pool` became `Draw.commit`:
   `announceDraw(metric, subjectKey, windowEnd, attempt, commit, beaconHeight)` stores
   `drawCommit(pool, spec, cfgHash) = keccak256("onyx-draw-commit-v1" ‖ pool ‖ spec ‖ cfgHash)`
   (pure view; Rust `observe::draw_commit`, vector `treasuryDraw.commit`, `poolHash`,
   `cfgHash`). `recordObservation(metric, subjectKey, windowEnd, spec, result, pool, cfgHash)`
   reverts `DrawMismatch` unless the fact's latest draw committed to exactly that pool, spec and
   config, so the window of a dated or period fact and the draw's `min_bond` are fixed before the
   beacon. `drawMatches(..., commit, ...)` compares it. Runtime 9,158 bytes (limit 24,576).

## Amendment (L16, 2026-10-16): the node pins the registry and keeps the attested level

THREATS L2R2-F2, L16-1..L16-5. A node serves a shard at the chain's level only when its
deployment manifest pins the registry, and that pin is now written and checked end to end:

1. **Export.** `demo-local --export-node` (used by `demo-local.sh`, `demo-testnet.sh` and
   `docker-smoke.sh`) writes `registry` and `registryCodeHash` whenever the run deployed
   `OnyxRegistry`. Before writing them it checks the runtime code at the broadcast's address is
   this checkout's build (forge `deployedBytecode`, only the `owner`/`ledger` immutables differ),
   so a proxy or other bytecode is never pinned (L16-1), and runs the node's own start check.
2. **Start check.** `levels::check_registry`: the code hash, then `ledger()` must be the
   manifest's `settlement` (L16-2). The code hash covers the immutables only when it is the real
   deployment's hash; the ledger binding holds even for a manifest naming another deployment's
   registry with that registry's matching hash. The start fails closed after its 8 tries.
3. **Level.** `onyx-node` cannot rate a pinned label set from a catalog file (it fails closed to
   level 5, L2R2-F3). With a pinned, checked registry the attested level stands in for that
   unknown label level (`ShardMeta::with_attested_level`): the registry refused any attestation
   stronger than the owner-registered label set level and the recipe floor, so the shard keeps
   its attested level. A catalog input level or a caller-supplied label level is never lifted;
   otherwise the chain's level only weakens. `/v1/health` reports `shardLevels` (served shards per level) and `shardsWithheld` (fallback, L16-R6).
4. **Trust.** Strengthening from 5 to the attested level trusts the registry owner's
   `registerLabelSet` (already the trust in this ADR; owner key hardening is H1).
5. **Review (L16-R1..R6).** The level is recomputed from its inputs on every setter (input
   floor; supplied label level, else the attested level, else 5; the weakest attestation), so
   no order of calls lifts a shard. An attestation counts only when its metric, recipe and label
   set are the catalog binding's. Money: under the money default (1 and 3) a labelled onyx-node
   shard settles only if its label set is registered at 3 or better; today's sets are level 4,
   so nothing more settles yet (L16-R4, lead to confirm before registering one at 3).
