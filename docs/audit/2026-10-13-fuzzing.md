# Rust fuzzing, 2026-10-13 (ROADMAP L3)

Branch `fuzz` from main `b2082cb`. Free, open-source tools only. Result: **18 cargo-fuzz
targets** over every parser on a trust boundary; **706 million executions** in two runs
(about 3.9 target-hours); **0 crashes found by the fuzzer**; **1 bug fixed** (FUZZ-1, an
integer overflow on a corrupt journal line, found while writing the `journals` harness and
reproduced with it). Five items stay open (FUZZ-2..6), none Medium or above.

## Tools

| Tool | Version |
|---|---|
| cargo-fuzz | 0.13.2 (`cargo install --locked cargo-fuzz`) |
| libfuzzer-sys | 0.4.13 (LLVM libFuzzer), `arbitrary` 1.5.0 |
| rustc (fuzz builds) | 1.101.0-nightly (`e9bbadf68` 2026-10-12), `rustup toolchain install nightly --profile minimal` |
| rustc (everything else) | 1.98.0 (pinned in `rust-toolchain.toml`; the fuzz crate also builds and lints on it) |
| cargo-audit | 0.22.2 on `fuzz/Cargo.lock`: 0 advisories, 210 crates |

Build flags: `cargo +nightly fuzz build -s none`: release optimizations **with debug
assertions and overflow checks** (cargo-fuzz's default), no sanitizer. The fuzzed code is
safe Rust (`unsafe_code = "deny"` in the workspace), so AddressSanitizer would mainly cover the
`secp256k1-sys` C library (FUZZ-2). Every run used libFuzzer's `-rss_limit_mb=2048` (an
allocation past 2 GiB is a crash) and `-timeout=10` (a 10 s input is a crash, so a stack
overflow or an unbounded loop is caught too). CPU: two targets at a time, one process each;
memory: every build and run under `systemd-run --user --scope -p MemoryMax=10G`.

## Layout

- `fuzz/`: its own Cargo workspace (`[workspace]` in `fuzz/Cargo.toml`), so the main workspace,
  CI and `scripts/check-all.sh` never build it and need no nightly. Its lockfile starts from the
  main one: every crate both use has the same version (only `libfuzzer-sys`,
  `derive_arbitrary`, `jobserver`, `getrandom 0.4`, `r-efi` are added).
- `fuzz/fuzz_targets/*.rs`: the 18 targets.
- `fuzz/common`: fixtures shared by the targets (an API server with one shard, one market and
  a mock x402 facilitator; scripted JSON-RPC nodes; the recorded level-2 round) and `seedgen`,
  which writes the seed corpus. No libFuzzer in it.
- `fuzz/seeds`, `fuzz/corpus`, `fuzz/artifacts`: generated, not committed (`fuzz/.gitignore`).
- `scripts/fuzz-smoke.sh`: opt-in; see "Running it".

## Finding fixed

**FUZZ-1** (Low; operator-local file; bug class: integer overflow on untrusted input).
`journal::Journal::open` replays lines `{"ops":[{"add": id, ...}]}` and set
`staged_next = id + 1`. A checksummed line naming `"add": 18446744073709551615` (the checksum is
damage detection, not a key, so anyone who edits the file can recompute it) panicked with
overflow checks on ("attempt to add with overflow", `journal.rs:230`), and in a release build
wrapped the next-id count to 0, after which the next entry written would take id 0 again. Every
journal shares this code: receipts, settle intents, pending self-settles, credits in flight.
Found by reading the replay code while writing the `journals` target; the target's first
60 s run did not reach the value on its own; the hand-written input crashed it (`deadly
signal`). Fix: ids are bounded by `journal::MAX_ID` = 2^53; a line with a larger id refuses the
open as damage, and `apply` refuses to give out ids past it. Test (stable, in `cargo test`):
`onyx-api journal::tests::fuzz_1_an_id_out_of_range_refuses_the_open` (the largest id still
reads, no id is given out past it, `MAX_ID` and `u64::MAX` refuse the open). The input is a
seed of the `journals` target, which runs it clean after the fix.

Borsh length prefixes (the "huge allocation" class) did not need a cap: borsh 1.8.1 (`de/mod.rs`, `de/hint.rs`) reads a
`Vec<u8>` in chunks of at most 1 MiB and preallocates other vectors only up to 4 KiB, so a
4-byte prefix of `0xffffffff` costs at most 1 MiB before the read fails; peak RSS of
`borsh_decode` stayed at 34 MB. No protocol type is recursive, so Borsh decoding has no stack
depth to exhaust; `serde_json` stops at depth 128.

## Running it

```
rustup toolchain install nightly --profile minimal      # once
cargo install --locked cargo-fuzz                       # once
scripts/fuzz-smoke.sh                                   # every target 30 s (18 x 30 s plus the build)
FUZZ_SECS=600 FUZZ_TARGETS="journals rpc_node" scripts/fuzz-smoke.sh
```

`scripts/fuzz-smoke.sh` regenerates the seeds, builds with `-s none`, runs each target and
prints execs, coverage and corpus per target; it exits 1 if any target crashes, leaving the
reproducer in `fuzz/artifacts/<target>/`. It is opt-in and not in `scripts/check-all.sh`
(nightly). A crash becomes a unit test on the stable toolchain, as FUZZ-1 did, so `cargo test`
keeps every fixed case. On the dev box run it under `systemd-run --user --scope -p
MemoryMax=10G`. Run 2026-10-13 after pass 2: exit 0, 18 targets, 0 crashes.
