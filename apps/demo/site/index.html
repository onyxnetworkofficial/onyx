4

Live: the latest blocks from a Bitcoin node

The same recipe and label set, run by the Rust engine on recent blocks fetched read-only from a Bitcoin Core node. Onyx checked every block from its raw bytes (a pinned minimum difficulty, proof of work, parent links, height, transaction Merkle root, witness commitment, fees). The live input is 16 MB, so your browser does not rerun the recipe here: it rechecks each header's proof of work against the pinned minimum difficulty and the parent links, and that the published root matches the published rows. An independent Python recount from the node's JSON gives the same numbers.

5

Validator: recompute and challenge

Validators rerun shards at random. Pick what a miner submitted. An honest result matches byte for byte. A miner who used other labels, or altered the blocks, is caught by recompute, not by a vote.

Choose a case and press Validate.

6

Commit, then reveal

Miners first publish only a hash that binds the root, the shard and their address with a secret salt. Nobody can copy a result they cannot see. After the round closes they reveal, and the settlement contract recomputes the same hash. The contract formulas already match Rust in shared test vectors; deployment on Base Sepolia comes in milestone 6.

7

First-party attestation

A label at 100% needs two signatures over one statement: the Bitcoin address signs (BIP-322), and a key the organisation registered with Onyx co-signs (EIP-191). One signature alone is refused, so nobody can claim an address for an exchange. This example uses test keys and a test entity.

Calibration scoring

      
Labelers state a probability. When ground truth arrives (an attestation), they are scored with the Brier rule over all registered organisations. Honest probabilities score best; overconfidence and empty "not this one" labels score worse. Lower is better.
